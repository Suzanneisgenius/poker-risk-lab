Poker Risk Lab: Understanding Uncertainty in Simulation

How much should we trust a simulated risk estimate? This is an interactive study of how numerical error, uncertain inputs and modelling assumptions affect a bankroll-risk estimate. Poker is the setting; the question applies to any simulated risk with an absorbing boundary.

Xinrui Song · Updated {{updated}} · How the numbers are checked

The short answer

For one scenario — 30 buy-ins, a +3 bb/100 win rate, 90 bb/100 swings, 100,000 hands — the model's exact risk of ruin is {{exact}}. A single simulation at the Risk Lab's default 2,000 paths lands within about {{n2000_half}} points of it. Not knowing the win rate after 50,000 hands leaves anything from {{u50_lo}} to {{u50_hi}} plausible, and five ways results might arrive give {{a_min}} to {{a_max}}. More computing only fixes the first.

The study does three things. It measures simulation error, with repeated runs, interval coverage, and checks against a closed-form value and independent implementations. It propagates uncertainty about the win rate, pushing a posterior through the risk formula instead of plugging in one number. And it stress-tests the assumptions: heavy tails, rare shocks and dependence at the same edge show which departures matter. Sections 1 to 3 below take these in turn.

A lower risk that was not a real change

After an engine update, the same settings and seed gave a lower risk: {{c_before}} → {{c_after}}. Two things had changed at once, the random numbers and how ruin is monitored, so each was switched on separately and then rerun over {{c_seeds}} seeds. The drop came from drawing different random numbers. The new monitoring raised risk on every seed and brought the average close to the exact value.

Details for

Same edge everywhere. Changing the shape of a 100-hand result barely moves risk ({{a_t}} with heavy tails, {{a_shock}} with rare shocks, against {{a_base}}). Letting swings carry over from one step to the next raises it to {{a_ar1}} (×{{a_ar1_x}}): each step still has the same spread, but the 100,000-hand total varies {{a_ar1_total}}× as much.

Method. {{a_paths}} paths per model, one seed. All five models are compared using ruin observed at 100-hand checkpoints; the bridge correction is exact only for Normal steps, so it is not used here. This holds the observation grid fixed. It does not establish equal monitoring bias across models or determine their continuously monitored ruin probabilities. Intervals are Wilson 95%.

Limits. These are controlled stress tests, not estimates of how real results arrive. The regime model's steps are also wider (standard deviation about {{a_regime_sd}} instead of 90).

Checking a misleading result

After the simulator changed, the same settings and seed gave a lower risk at +3 bb/100: {{c_before}} → {{c_after}}. A lower risk is easy to read as an improvement. Two things had changed at once — how ruin is monitored and how random numbers are drawn — so each was switched on separately.

  1. Fix everything else. Same inputs, same seed, called directly through the calculation function.
  2. Change one thing at a time. New random numbers alone: {{c_before}} → {{c_stream}} ({{c_stream_pp}} points, a different random sample). Adding the bridge correction: → {{c_after}} (+{{c_bridge_pp}} points).
  3. Look beyond one seed. Over seeds 0–39 the correction raised risk for every seed, by {{c_mean_pp}} points on average, and brought the average to {{c_mean}} against the exact {{exact}}.
  4. Conclusion. The drop was sampling, not a change in risk; the correction itself pushes the number up, as it should. The release notes say so, and every saved result now records the engine version.

Reproduce

Each figure on this page comes from one command and one configuration file. The outputs record the commit, seeds, path counts and software versions; this page is built from them by npm run build.

Install with pip install -r requirements-research.txt. Validation checks have their own commands on the Validation page.

What this does not show

  • That any of these models describes real poker results. Agreement with the exact value checks the arithmetic, not the model.
  • A recommended bankroll. Every number is a conditional model estimate, not financial or gambling advice.
  • Anything about the Preflop ranges, which are illustrative demonstration data.
